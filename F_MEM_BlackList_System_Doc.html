用途

以電話號碼或 USER_ID 查出任一會員（不分是否被標記黑名單），並針對查到的帳號進一步做兩件事：反查它近期登入過的 IP 底下還有哪些其他帳號（抓同一人／同一裝置註冊多帳號規避封鎖），以及查它近期的訂票紀錄（抓短時間大量下單的搶票機器人特徵）。系統並依既定門檻，對每筆結果自動給出「請IT確認／保持封鎖／可解封鎖／通知IT確認」四種提示。

使用者與存取限制

  • 使用對象：營運／客服／IT 人員，用於個案查核，非給一般使用者瀏覽。
  • 頁面內建 IP 白名單（9 組內部 IP），不符者整頁替換為「存取被拒絕」。
  • 資料含 USER_ID、MOBILE 等會員個資，屬受限資料。
⚠️ 白名單是「顯示層」保護，不是存取控制。該檢查在瀏覽器端執行（呼叫 api.ipify.org 比對後才把頁面顯示出來），會員資料本身已內嵌在 HTML 檔案裡。任何能連到這個檔案的人（例如直接以 curl 抓檔）都能讀到全部內嵌資料，不會經過這道檢查。真正的邊界是內部網段與站台本身的存取控制。

為什麼是靜態內嵌而不是即時查詢

  • 頁面是純靜態檔案，不能把 MongoDB 連線字串放進前端 JS，否則等同外洩整個資料庫存取權。
  • 來源 collection 皆只有 _id 索引，逐帳號即時查詢需全表掃描（單次約 0.7 秒起跳），互動體驗不可行。
  • 2026/08/06 曾改用 Vercel serverless API 即時查詢，隔日回退：Vercel 無固定 outbound IP，而 QwareAi 這個 Atlas 專案的 Network Access 未開放 0.0.0.0/0，連線不穩。若未來要重啟 API 方案，必須先解決 Atlas Network Access。

產出機制（marker 注入）

generator 不重建整份 HTML，而是把既有檔案裡兩個 marker 之間的內容整段換掉，因此版面／JS 邏輯的手動修改不會被覆蓋：

// ── Data Start ──────────────────────────────────────────────────────────────
const BLACKLIST_DATA = […];
const DATA_META = {…};
const IP_LINKS = {…};
const ALL_INDEX = […];
const BOOKING_DATA = {…};
// ── Data End ────────────────────────────────────────────────────────────────
⚠️ marker 字串不可修改，否則 generator 會拋 Data markers not found 而整支失敗。另外 <span id="updateTimeLabel"> 會被 regex 換成執行當下時間。

{ u:"32322139317825347177", // USER_ID
  h:"852", m:"94702125",     // 國碼、完整電話
  f:null,                    // MEMO0 原始值（'Y'/'N'/'4'/null）
  ct:"2023-10-03 16:41:15",  // CREATE_TIME（台北時間）

  wty:"APPLE" }              // webType 原始值（登入來源）

5功能說明

5.1 查詢模式（二選一，互斥）

「電話號碼」（預設）與「USER_ID」兩種模式，同一時間只有選中模式的輸入框可用，另一框會被 disabled，即使殘留舊文字也不會被讀取。兩者皆對 ALL_INDEX 做 includes 部分字串比對，輸入即時篩選（綁 oninput）。電話比對的是不含國碼的完整號碼。

頁面載入時不預先顯示任何資料，需主動查詢才出現表格；「重置」會清空輸入、切回電話模式並回到空白狀態。

5.2 結果表格（9 欄）

USER_ID ｜ 黑名單狀態 ｜ MOBILE ｜ 登入來源 ｜ CREATE_TIME ｜ CREATE_USER ｜ UPDATE_USER ｜ 關聯帳號 ｜ 訂單紀錄。前 7 欄可點欄位標題排序，預設依 UPDATE_TIME 新到舊；最後兩欄為操作按鈕。

  • 黑名單狀態：黑名單（MEMO0='Y'）／未標記（null）／4 等其他值原樣顯示。
  • MAJOR 標籤：MAJOR 顯示於 USER_ID 旁，代表該門號對應 5 個以上不同 USER_ID。
  • 登入來源：webType 原始值，以顏色徽章呈現（見 §9）。

5.3 關聯帳號 modal

按鈕顯示「🔗 IP關聯 (N)」（N＝近 30 天用過的相異 IP 數）或「🔗 無登入紀錄」。點開後依序列出：每個 IP 與該帳號在此 IP 的最後登入時間 → 同一 IP 下的其他帳號（依最後登入時間新到舊，最多 30 個）→ 若被截斷則顯示「共 N 個共用帳號，僅顯示前 30 個」。

每 IP 上限 30 的原因：實測有少數 IP 被 2,000＋不相關帳號共用（電信商 CGNAT／公共網路出口），屬非真實關聯，不設限會把檔案撐爆。

5.4 訂單紀錄 modal

按鈕顯示「🎫 訂單 (N)」或「🎫 無訂單紀錄」。點開列出該帳號近 7 天全部訂票紀錄（演出代碼、座位、訂票 IP、訂票時間），依時間新到舊，不設筆數上限——同一帳號短時間內重複訂同一批座位本身就是重點訊號，截斷反而會把它藏起來。

ℹ️ MAJOR 門檻為何是 5 而不是 2：原始需求是「出現兩個以上」，但門檻 2 會命中全體會員的 78%（24.6 萬組門號裡有 15.6 萬組本來就對應 2 個以上帳號，是這份資料的常態），完全失去辨識力。改為 5 後命中約 0.24%，恢復可用性。要調整敏感度改 generator 裡的 MAJOR_THRESHOLD 常數即可。

8設計限制與已知風險

8.1 檔案大小逼近 GitHub 硬性上限 高風險

目前檔案約 94 MB（98,935,207 bytes），GitHub 對單一檔案的硬性上限是 100 MiB，超過即直接拒絕 push。體積成長史：全會員索引 +25MB → 索引補時間欄位 +35MB → 訂單紀錄 +17MB → webType 欄位 +9MB。

🚨 此風險已實際發生過。2026/08/13～08/17 產出的版本膨脹到 105～110 MB，git push company 被 pre-receive hook 全批拒絕，ticket-uat 的 ReportNew 站台所有報表停留在 08/12 達六天，直到 2026/08/18 把待推的 18 個 commit 壓成單一 commit（只帶當前 98.9MB 的版本）才恢復。日排程每天都有發出 LINE 失敗告警。

後續選項（尚未決定）：縮小時間窗或欄位、拆分報表、改用 Git LFS（需確認 company repo 與 IIS 部署流程支援）、或重啟後端 API 方案（需先開通 Atlas Network Access）。

8.2 逐字輸入可能讓瀏覽器卡死 中風險

applyFilter() 綁在 oninput，沒有最短字元數門檻，也沒有渲染筆數上限。從空白開始逐字輸入時，單一字元（例如「0」）可能比對到數十萬筆電話號碼，並嘗試建立等量 <tr> 節點，實測可讓分頁失去回應數十秒。目前無實際使用者投訴，列為已知限制。改善選項：設最短查詢字元數（如 4 碼）、限制渲染筆數（如前 200 筆）、或改回「按套用篩選才查」。

8.3 告警可能少報一個失敗項 中風險

daily_update.bat 推送區塊（if errorlevel 1 (…) else (…)）內以 %FAILED_STEPS% 而非 !FAILED_STEPS! 累加失敗名稱。批次檔會在解析整個區塊時就展開 %…%，因此當 origin 與 company 兩個 push 都失敗時，後者的賦值會覆蓋前者，LINE 告警只會提到 NewReport-push-company。判讀告警時請直接檢查 git_sync.log，不要只看告警字串。

8.4 資料範圍限制（非缺陷）

  • 查得到帳號、但「關聯帳號」顯示無登入紀錄 → 該帳號不在近 30 天黑名單範圍內，屬正常。
  • 更早期的黑名單異動紀錄本報表查不到，需另行以 MongoDB 查詢。
  • 來源 collection 名稱含年月（…_202608）。跨月時若上游改用新 collection，generator 需同步改名，否則資料會停在舊表。

8.5 產出失敗的常見原因

2026/08/15、08/16 兩次 generator 失敗皆為 MongoDB 連線逾時（MongoNetworkTimeoutError / PoolClearedOnNetworkError），非邏輯錯誤——全表掃描 53 萬筆＋50 萬筆登入紀錄對 Atlas 壓力較大，偶發逾時重跑即可。

webType（登入來源）

MongoDB 原始欄位（camelCase，非 WEB_TYPE），全體會員皆有值，共 6 種。研判為註冊／登入管道，但 OP 與 MAJOR 的確切業務意義未經業主證實，系統只如實顯示原始值、不臆測。

🍎 APPLE 📘 FB 🔍 GOOGLE 💬 LINE ⭐ MAJOR OP （約 MAJOR 46%／OP 25%／GOOGLE 19%／LINE 7%／APPLE 3%／FB <1%）

⚠️ 兩個 MAJOR 完全無關。登入來源欄的橘色 ⭐ MAJOR 是資料庫 webType 的其中一個值；USER_ID 旁的紫色 MAJOR 是本系統自行計算的「同門號 5+ 帳號」旗標。只是字串恰好同名，刻意用不同顏色與圖示區隔。
